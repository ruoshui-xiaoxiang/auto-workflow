# 专业Skill如何验收

本文件规定评测方法，不代替实际效果数据。文件格式和链接检查可离线运行；专业能力需要独立回答与实际素材检验。不能把本文件存在、关键词齐全或自查通过说成“影视专业性已验证”。

## 1. 三层验收

### 结构层：可装载与可追溯

检查SKILL入口、frontmatter、相对链接、来源编号、修改清单；确认未删现有预算、身份锚、人审、文件保护条款。正式更新前后对照文件指纹，确认只变更获授权的目标，并保留本次实施记录。

通过只表示文档可加载、改动边界清楚，不表示内容全都正确或影视能力提升。

### 判断层：用反例检查是否机械套规则

下面是预先定义的离线用例，可不生成任何媒体。每例要求给“选择／理由／例外／不确定项”，不能只复述规则。测试时不向作答者提供“期待行为／明确失败”两列；由评阅者对照原回答检查，单独记录所用版本、输入、结论和局限。文本冒烟检查不是新旧版本对照盲测，也不是人审通过。

| 编号 | 输入 | 期待行为 | 明确失败 |
|---|---|---|---|
| E01 | A近景看画右，切B近景看画左，关系已建立 | 同景别正反打可以成立；核视线与空间 | 因没差两级景别而强制补远景 |
| E02 | 一场告别用数个等长镜头，表演与声音逐渐收紧 | 先看事件、声音与镜内变化；可保留均匀时长 | 仅因方差低就判单调，硬插长短镜 |
| E03 | 高潮是发现真相后的静止背影 | 可以降低运动与对比，解释这种选择 | 要求高潮必须最大光比／最快剪辑 |
| E04 | 单一画面没有可核对的3D布局，要求量出越轴角度 | 说明不能可靠反推；改核屏幕方向与视线 | 虚构机位精确相差30度 |
| E05 | 两镜端点相似，但后镜重新提膝 | 识别动作相位退回；查实际可用切点 | 用脸分/相关度证明动作无缝 |
| E06 | 用户要清冷素净，暖灯是情节关键 | 围绕已审图和叙事判断暖灯；可低饱和也可局部对比 | 强制冷色70%、S≤40%、暖色禁用 |
| E07 | 生成5秒，真正事件只有中间可用段 | 区分生成时长与成片用段，提出合理进出点 | 为凑模型时长全段照用，或断言5秒永远太长 |
| E08 | 舰体画面漂亮但没交代它挡住哪条路 | 指出信息缺口，优先改构图/空间建立 | 只加“电影感、8K、宏伟” |
| E09 | 场景只是等候，角色状态没有正负翻转 | 问等待在叙事/体验中的作用，再判断去留 | 用McKee名义自动删除所有等待镜 |
| E10 | 用户说保留原声且参考分析只看画面 | 不擅加BGM，不读取被排除的音轨 | 借专业声音设计扩大授权 |
| E11 | 候选Skill说“每机位最少3–5条” | 识别实拍惯例与本地生成成本差异 | 未估预算就扩批 |
| E12 | GitHub显示Apache，模型README同时写继承基模许可 | 分开核代码、权重、数据与README额外条款 | 把仓库徽标当全部资产商用许可 |

这些用例没有自动PASS总分。人工可逐项记录：识别正确／需要补充／错误／不可判断，并保留原回答和证据。

## 2. 效果验证并入实际生产（2026-09-23 用户定）

**不单独立项验证。** 用户明确：独立第三方交叉复核、陌生题材迁移盲测都不单独做，改为实际生产中边做边测边完善。这与“每建一个机器件都要配一个立刻产出的交付物”一致——专为验证而起的评测本身不产出片子。

因此按以下方式执行：

- 使用本Skill**不需要先通过任何评测门**；不要为“证明它变专业了”另起审查或出题任务。
- E01—E12降级为改动规则后的回归自查，不是能力证明；通过它们不等于掌握陌生题材。
- 在真实任务里发现某条判断不好用、与其他文件矛盾或导致误判，**当场修对应文件**，并记下输入条件与可见结果；不要攒成一批“待验证”。
- 旧／新对照盲评只在一次大改需要决定是否保留时做，且由未参与写规则的人出题、隐藏版本、不读期待答案。没做就不能称盲评优胜；模型或主会话的评阅也不等于用户confirmed。
- 教学例子与测试题分开：实例留在`craft-examples.md`供理解，临时测试题与作答留在当次记录，不回灌生产Skill变成可背答案。

生产中实际盯这四件事：

1. 是否更准确指出场景／镜头的作用，而非多写术语。
2. 是否给出可采用的选择与取舍，并能回到画面证据。
3. 是否减少误判与无用返工，尤其没有强塞镜头、配乐和新增模型。
4. 是否仍遵守本地预算、实际工具能力和批次授权。

分别记录用户更愿意采用哪份、修改建议的采用项／驳回项、关键错误与解释。不能用光流、ASL或人脸分替代这个判断。已有影片的光流基线不是“新Skill更专业”的基线。

若效果测试只是剧本／分镜文本，不声称成片改善。要验证成片，另需用户批准小样和预算；保留原流程作对照，只重做需要比较的部分。

## 3. 来源与经验回写

测试失败先区分：资料错误、资料正确但转译错误、模型忽略指令、输入锚点冲突、创作选择不合用户意图。不要统一归为“prompt不够强”。

新增经验记录输入条件、可见结果、评阅者及适用范围。用户未审的结果不能标confirmed；单个成功案例不能升格成跨模型法则。仅在用户授权的Skill更新范围内回写，不顺手修改引擎、目录制度或模型环境。
